# Split-Repo Releases

Two repositories instead of one: an **application repository** owning service
source, tests, and its build; an **infrastructure repository** owning `Terraform/`
and `scripts/`. The monorepo release — build and apply in one job, one run, one
repository — becomes two pipelines with an explicit artifact handoff between them.

Everything else in this skill is unchanged. The Terraform tree is identical, the
per-stack `deploy-*.sh` / `destroy-*.sh` bodies are identical, and the plan-on-PR
/ apply-on-merge gate is identical. Only the artifact handoff and the CI wiring
differ. Read [`ci-workflows.md`](ci-workflows.md) first; this file is the delta.

## When To Split

Split when the boundary is an **ownership** boundary: application code and
infrastructure have different teams, different review paths, or must not share
deployment credentials. Do not split merely to have smaller repositories — a
single team shipping a single service pays the handoff cost for no gain.

Prefer **one application repository holding several services** over one repository
per service. That gets the ownership boundary without N copies of near-identical
release CI, which is the same reasoning that made
[`ci-workflows.md`](ci-workflows.md) choose one reusable workflow plus thin
callers.

The cost is concrete and worth stating before adopting it: **the atomic commit
disappears.** A change that needs both sides — a new environment variable plus the
code that reads it, a memory increase plus the workload that needs it — becomes
two pull requests in two repositories with an ordering constraint that nothing
enforces for you. Sequence it deliberately: land the infrastructure change that is
backward compatible with the running code first, then release the code.

The gain is also concrete. In a monorepo, a push to application source reaches a
role that runs `terraform apply`. After the split, the application repository holds
a **publish-only** role and cannot apply anything at all.

## The Invariant

**The build travels with the source; the apply travels with the Terraform.**

`build-<service>.sh` moves to the application repository, because it reads source
and stamps the artifact with the source commit. `deploy-app-<service>.sh` and
`destroy-app-<service>.sh` stay in the infrastructure repository, because they
read `Terraform/`. Nothing needs to reach across the boundary at runtime.

A build script left in the infrastructure repository is the single most common way
this goes wrong: `GIT_SHA="$(git -C "$REPO_ROOT" rev-parse HEAD)"` then stamps the
artifact with the *infrastructure* commit, so the image tag no longer identifies
the code inside the image.

## Who Owns What

| | Application repository | Infrastructure repository |
|---|---|---|
| Source | `apps/<service>/`, `lambdas/<service>/` | — |
| Tests | unit and integration tests for the service | `terraform test`, `tflint`, `trivy` |
| Build | `scripts/build-<service>.sh` | — |
| Terraform | — | all of `Terraform/` |
| Deploy scripts | — | `deploy-app-<service>.sh`, `destroy-app-<service>.sh`, orchestrators |
| Artifact registry | publishes to it | reads from it |
| AWS role | publish-only | apply for one stack per environment |
| Deploy history | what each artifact contains | which artifact is deployed where |

Neither repository's history answers "what is running in production" alone. The
infrastructure repository says *which version*; the application repository says
*what that version contains*. Keep both answerable — see the comment header in
[the artifact file](#the-handoff-a-committed-artifact-file).

## The Handoff: A Committed Artifact File

The application repository publishes an immutable artifact, then opens a pull
request against the infrastructure repository that changes one file:

```text
Terraform/environments/{env}/{stack}.artifacts.tfvars
```

```hcl
# Generated by <org>/app-notifier — do not edit by hand.
# source_repo:   <org>/app-notifier
# source_commit: 9f2c1ab4e77d
# workflow_run:  https://github.com/<org>/app-notifier/actions/runs/1234567890
notifier_lambda_s3_key            = "lambdas/notifier/7b3c…f0.zip"
notifier_lambda_s3_object_version = "kFz9_QhE2mNq1pR4sT7uV0wX3yZ6aB8c"
notifier_lambda_source_code_hash  = "K4uS0lB2vN8xQ6zT1yR3pM7wJ9cH5dF2gE0aI4kL6oM="
```

Four properties make this the default:

- **Every deploy is a reviewable diff.** The existing `infra-plan.yml` triggers on
  `Terraform/**`, so the pull request gets a plan with no new workflow.
- **`git log` in the infrastructure repository is the deploy history**, per
  environment, with no external system to query.
- **Rollback is `git revert`** — the previous artifact is still in S3 or ECR
  because both are immutable, so no rebuild is involved.
- **Promotion is a one-line diff** between two environments' files.

Two rules about the file itself:

- **Keep it separate from `{stack}.tfvars`.** That file is human-owned and
  hand-edited; this one is machine-written and overwritten wholesale. Merging them
  guarantees a conflict between an operator's memory change and a release.
- **Commit it, and gitignore nothing.** This is the one artifact-version file that
  is committed. The generated file under `build/` still exists in monorepo mode
  and stays gitignored; do not commit both for the same stack.

The values are non-secret coordinates — a key, an object version, a content hash,
an image tag or digest. Committing them is safe. Committing a value the artifact
*contains* is not; nothing about this file changes the rule that secrets stay out
of tfvars.

## Deploy Script Changes

One line, and one guard. `ARTIFACT_VARS` resolves to the committed file rather
than to the build output:

```bash
# Split-repo mode: the artifact version is published by the application
# repository as a committed file. Monorepo mode reads build/<service>/ instead.
ARTIFACT_VARS="$REPO_ROOT/Terraform/environments/$ENV/$LOGICAL_STACK.artifacts.tfvars"

if [[ ! -f "$ARTIFACT_VARS" ]]; then
  print_error "Missing $ARTIFACT_VARS"
  print_error "No artifact has been published for $LOGICAL_STACK in $ENV."
  print_error "Run the release workflow in the application repository that owns this service."
  exit 1
fi
```

Then pass both files, in this order, everywhere the script plans:

```bash
terraform plan -input=false -lock-timeout=5m \
  -var-file="$VAR_FILE" -var-file="$ARTIFACT_VARS" -out="$PLAN_FILE"
```

Fail on the missing file rather than defaulting. The rule that a release which
skipped its build fails at plan instead of silently redeploying the previous
artifact is what keeps a broken pipeline from looking like a successful deploy;
the split does not relax it.

Do not add a fallback that tries the committed file and then the build directory.
An implicit fallback is how a stale local build silently wins over the reviewed
version.

## The Application Repository's Workflow

```yaml
# .github/workflows/release-notifier.yml (application repository)
name: release-notifier

on:
  push:
    branches: [main]
    paths:
      - 'lambdas/notifier/**'
      - '.github/workflows/release-notifier.yml'
  workflow_dispatch:
    inputs:
      environment:
        required: true
        type: choice
        options: [dev, staging, prod]

permissions:
  contents: read
  id-token: write

concurrency:
  group: release-notifier-${{ inputs.environment || 'dev' }}
  cancel-in-progress: false

jobs:
  test:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: lambdas/notifier
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
      - run: uv lock --check
      - run: uv sync --frozen
      - run: uv run --frozen pytest

  publish:
    needs: test
    runs-on: ubuntu-latest
    environment: ${{ inputs.environment || 'dev' }}
    env:
      ENV: ${{ inputs.environment || 'dev' }}
      LAMBDA_ARTIFACT_BUCKET: ${{ vars.LAMBDA_ARTIFACT_BUCKET }}
    steps:
      - uses: actions/checkout@v4

      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::${{ vars.AWS_ACCOUNT_ID }}:role/ArtifactPublishRole-notifier-${{ inputs.environment || 'dev' }}
          aws-region: ${{ vars.AWS_REGION }}

      - name: Build and publish the artifact
        run: ./scripts/build-notifier.sh

      - name: Mint a token for the infrastructure repository
        id: token
        uses: actions/create-github-app-token@v1
        with:
          app-id: ${{ vars.INFRA_BOT_APP_ID }}
          private-key: ${{ secrets.INFRA_BOT_PRIVATE_KEY }}
          owner: ${{ github.repository_owner }}
          repositories: infra

      - name: Open the release pull request
        env:
          GH_TOKEN: ${{ steps.token.outputs.token }}
          ENVIRONMENT: ${{ inputs.environment || 'dev' }}
        run: ./scripts/open-release-pr.sh
```

`build-notifier.sh` is unchanged from
[`build-scripts.md`](build-scripts.md) except that it writes its tfvars body to a
path the next step reads. `open-release-pr.sh` clones the infrastructure
repository shallowly, writes the file, and opens the pull request:

```bash
#!/usr/bin/env bash
# Publish this service's artifact version to the infrastructure repository.
set -euo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
REPO_ROOT="$(cd "$SCRIPT_DIR/.." && pwd)"
SERVICE="notifier"
STACK="app-$SERVICE"
ENVIRONMENT="${ENVIRONMENT:?Set ENVIRONMENT to the target environment}"
INFRA_REPO="${INFRA_REPO:-<org>/infra}"
ARTIFACT_BODY="$REPO_ROOT/build/$SERVICE/$SERVICE-artifacts.tfvars"
WORK_DIR="$(mktemp -d)"
BRANCH="release/$SERVICE-$ENVIRONMENT-$(git -C "$REPO_ROOT" rev-parse --short=12 HEAD)"

# Paste the four print_* helpers verbatim (SKILL.md -> Helper Functions).

trap 'rm -rf "$WORK_DIR"' EXIT

for cmd in gh git; do
  if ! command -v "$cmd" &>/dev/null; then print_error "$cmd is not installed"; exit 1; fi
done
[[ -f "$ARTIFACT_BODY" ]] || { print_error "Build did not produce $ARTIFACT_BODY"; exit 1; }

SOURCE_COMMIT="$(git -C "$REPO_ROOT" rev-parse HEAD)"
RUN_URL="${GITHUB_SERVER_URL:-https://github.com}/${GITHUB_REPOSITORY:-local}/actions/runs/${GITHUB_RUN_ID:-0}"

gh repo clone "$INFRA_REPO" "$WORK_DIR" -- --depth=1
git -C "$WORK_DIR" checkout -b "$BRANCH"

TARGET="$WORK_DIR/Terraform/environments/$ENVIRONMENT/$STACK.artifacts.tfvars"
mkdir -p "$(dirname "$TARGET")"
{
  printf '# Generated by %s — do not edit by hand.\n' "${GITHUB_REPOSITORY:-$INFRA_REPO}"
  printf '# source_repo:   %s\n' "${GITHUB_REPOSITORY:-unknown}"
  printf '# source_commit: %s\n' "$SOURCE_COMMIT"
  printf '# workflow_run:  %s\n' "$RUN_URL"
  cat "$ARTIFACT_BODY"
} >"$TARGET"

if git -C "$WORK_DIR" diff --quiet -- "$TARGET"; then
  print_info "No artifact change for $SERVICE in $ENVIRONMENT — nothing to release"
  exit 0
fi

git -C "$WORK_DIR" add "$TARGET"
git -C "$WORK_DIR" -c user.name="release-bot" -c user.email="release-bot@users.noreply.github.com" \
  commit -m "release($SERVICE): $ENVIRONMENT to ${SOURCE_COMMIT:0:12}"
git -C "$WORK_DIR" push -u origin "$BRANCH"

gh pr create --repo "$INFRA_REPO" --head "$BRANCH" --base main \
  --title "release($SERVICE): $ENVIRONMENT to ${SOURCE_COMMIT:0:12}" \
  --body "Automated release of \`$SERVICE\` to \`$ENVIRONMENT\`.

Source: ${GITHUB_REPOSITORY:-unknown}@$SOURCE_COMMIT
Run: $RUN_URL"
```

Four details that break this if missed:

- **Use a GitHub App installation token, not `secrets.GITHUB_TOKEN`.** The default
  token cannot reach another repository at all, and a pull request opened by an
  Actions token does not trigger `on: pull_request` workflows — so
  `infra-plan.yml` would never run and the release would merge unplanned. An App
  token scoped to the infrastructure repository with `contents: write` and
  `pull-requests: write` avoids both problems and is preferable to a personal
  access token, which carries a human's full access and expires on their offboarding.
- **Exit 0 on no change.** Re-running a release for an already-published version
  must be a clean no-op, not an empty pull request.
- **Branch per source commit and environment.** Two releases in flight for
  different environments must not fight over one branch.
- **`concurrency` with `cancel-in-progress: false`.** Cancelling mid-publish can
  leave an artifact in the registry with no pull request pointing at it — harmless
  but confusing — and cancelling two racing runs can land them out of order.

## The Infrastructure Repository's Workflow

`_app-release.yml` loses its build step and its `SERVICE` environment variable —
there is no build script here to consume it — and keeps everything else, including
the `service` input, because the deploy role is still named after the service:

```yaml
# .github/workflows/_app-release.yml (infrastructure repository)
on:
  workflow_call:
    inputs:
      service:
        required: true
        type: string
      stack:
        required: true
        type: string
      environment:
        required: false
        type: string
        default: dev

permissions:
  contents: read
  id-token: write

jobs:
  release:
    runs-on: ubuntu-latest
    environment: ${{ inputs.environment }}
    concurrency:
      group: tfstate-${{ inputs.stack }}-${{ inputs.environment }}
      cancel-in-progress: false
    env:
      CI: 'true'
      ENV: ${{ inputs.environment }}
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::${{ vars.AWS_ACCOUNT_ID }}:role/AppDeployRole-${{ inputs.service }}-${{ inputs.environment }}
          aws-region: ${{ vars.AWS_REGION }}
      - run: ./scripts/deploy-${{ inputs.stack }}.sh
```

Keeping `AppDeployRole-<service>-<env>` identical to
[`ci-workflows.md`](ci-workflows.md) matters: the role names, the generating
`setproduct` module, and the state prefixes all stay the same across a
monorepo-to-split migration, so only the trust policies change.

The per-service caller's `paths:` filter changes from application source to the
artifact file, because application source is no longer in this repository:

```yaml
# .github/workflows/release-app-notifier.yml (infrastructure repository)
on:
  push:
    branches: [main]
    paths:
      # dev only, deliberately: this trigger always applies ENV=dev. Every other
      # environment promotes through workflow_dispatch — a wildcard here would
      # apply dev on a merge that changed staging's file.
      - 'Terraform/environments/dev/app-notifier.artifacts.tfvars'
      - 'Terraform/stacks/app-notifier/**'
  workflow_dispatch:
    inputs:
      environment:
        required: true
        type: choice
        options: [dev, staging, prod]

jobs:
  release:
    uses: ./.github/workflows/_app-release.yml
    with:
      service: notifier
      stack: app-notifier
      environment: ${{ inputs.environment || 'dev' }}
    secrets: inherit
```

**The single-environment path filter is load-bearing.** The push trigger carries no
environment of its own — the job applies whatever `ENV` resolves to, which on a
merge is the literal `dev`. Widen the filter to
`Terraform/environments/*/app-notifier.artifacts.tfvars` and a merge that changed
only `staging`'s file fires a release that applies **dev**: a green run that
shipped nothing to the environment under review, and shipped dev whatever happened
to be sitting in dev's file. Match one environment per push trigger, and let every
other environment reach production through `workflow_dispatch`
([Promotion and Rollback](#promotion-and-rollback)).

The `Terraform/stacks/app-notifier/**` entry is fine on the same trigger: a stack
change should redeploy dev, which is exactly what `ENV=dev` does.

The alternative — a job that derives the environment from the changed path — is
rejected for the same reason [`ci-workflows.md`](ci-workflows.md) rejects deriving
the role from the changed-files list. A literal in a committed workflow is
reviewable and is independently constrained by the role's trust policy; a value
computed from a diff is neither, and here it would select which environment an
apply lands in.

If several environments must auto-deploy on merge, give each one its own caller
file with its own single-environment filter and its own `environment:` literal.
That is a few more ten-line files and keeps every environment a reviewable
constant.

`infra-plan.yml` needs no change at all. Its `Terraform/**` filter already covers
the artifact file, so every release pull request gets a plan under the read-only
role, which is the whole reason to route the handoff through git.

## Roles Under The Split

The single applying role becomes two narrower ones, in two different trust
domains.

`ArtifactPublishRole-<service>-<env>` in the application repository may publish an
artifact and nothing else:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublishLambdaArtifact",
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject"],
      "Resource": "arn:aws:s3:::<artifact-bucket>/lambdas/notifier/*"
    },
    {
      "Sid": "VerifyBucketVersioning",
      "Effect": "Allow",
      "Action": "s3:GetBucketVersioning",
      "Resource": "arn:aws:s3:::<artifact-bucket>"
    }
  ]
}
```

For a container service, substitute `ecr:GetAuthorizationToken` plus the push
actions on that one repository. It holds **no** Terraform state access, **no**
`lambda:UpdateFunctionCode`, **no** `ecs:UpdateService`, and **no**
`iam:PassRole`. A compromised application pipeline can publish an artifact nobody
approved; it cannot deploy one.

Its trust policy pins the application repository:

```json
{
  "Condition": {
    "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" },
    "StringLike": { "token.actions.githubusercontent.com:sub": "repo:<org>/app-notifier:environment:prod" }
  }
}
```

`AppDeployRole-<service>-<env>` keeps everything
[`ci-workflows.md`](ci-workflows.md) grants it, minus artifact-publishing rights —
it now only reads the artifact — and its trust policy pins the **infrastructure**
repository:

```json
{
  "StringLike": { "token.actions.githubusercontent.com:sub": "repo:<org>/infra:environment:prod" }
}
```

The `sub` claim is per-repository, so this is the step that actually enforces the
split. Getting it wrong in the permissive direction — listing both repositories in
one trust policy — silently restores the monorepo's blast radius while looking
like a split.

Both roles are still platform-tier resources, applied by `infra-apply.yml`, and
still generated from the `setproduct` module in
[`ci-workflows.md`](ci-workflows.md) — now with two role kinds and two repository
subjects.

## Promotion and Rollback

Promotion is copying three lines between two environments' artifact files:

```sh
cp Terraform/environments/dev/app-notifier.artifacts.tfvars \
   Terraform/environments/staging/app-notifier.artifacts.tfvars
```

Open that as a pull request, read the plan, merge, then dispatch the release for
`staging`. The diff states exactly which version is moving and which one it
replaces, which a `workflow_dispatch` promotion cannot.

Rollback is `git revert` of the release commit, then the same release path. The
artifact it points back at is still in S3 or ECR because both are immutable, so
nothing rebuilds and the restored version is bit-identical to what ran before.
Reverting the *application* repository instead would rebuild at an older commit —
slower, and only bit-identical if the build is reproducible.

For an urgent production rollback where a pull request is too slow, dispatch the
release workflow with the previous version supplied directly, then land the revert
afterwards so git and reality agree. Leaving that reconciliation undone is how the
committed file stops being trustworthy.

## Bring-Up Without A Build

`deploy.sh` in the infrastructure repository cannot build application artifacts —
it does not have the source. So a bring-up of a new environment hits every app
stack's required, no-default artifact variable and fails at plan. That failure is
correct; the fix is sequencing, not a default value:

1. Apply the platform tier: `deploy-platform.sh`. This creates the artifact
   bucket, the ECR repositories, and the published SSM contract.
2. From each application repository, dispatch its release workflow against the new
   environment. Each one publishes an artifact and opens a pull request adding
   `Terraform/environments/<new-env>/app-<service>.artifacts.tfvars`.
3. Merge those, then run `deploy.sh` — or each `deploy-app-<service>.sh` — with
   every artifact file now present.

The inline build call between stacks in
[`orchestrators.md`](orchestrators.md) has no split-repo equivalent. Delete it
rather than replacing it with a cross-repository clone: a bring-up script that
clones and builds N application repositories needs credentials for all of them,
which reassembles the blast radius the split removed.

State this in `deploy.sh`'s pre-flight so the failure is self-explaining rather
than N stack failures deep:

```bash
MISSING=()
for entry in "${APP_STACKS[@]}"; do
  stack="${entry%%:*}"
  [[ -f "$REPO_ROOT/Terraform/environments/$ENV/$stack.artifacts.tfvars" ]] || MISSING+=("$stack")
done
if (( ${#MISSING[@]} > 0 )); then
  print_error "No published artifact for $ENV: ${MISSING[*]}"
  print_error "Release each service from its own repository before bringing up app stacks."
  exit 1
fi
```

## Destroy Needs The Artifact File

`destroy-app-<service>.sh` runs `terraform plan -destroy` with `-input=false`.
A required, no-default artifact variable makes that plan fail on a missing value
even though a destroy never uses the artifact. Pass the artifact file to the
destroy plan too:

```bash
terraform plan -destroy -input=false -lock-timeout=5m \
  -var-file="$VAR_FILE" -var-file="$ARTIFACT_VARS" -out="$DESTROY_PLAN_FILE"
```

This applies in monorepo mode as well, where the file lives under `build/` and may
not exist at destroy time. In split mode the committed file is always present,
which is one more reason to prefer it. If a destroy must run when no artifact was
ever published, supply a syntactically valid placeholder with `-var` on that one
invocation and never write it into a committed file.

## Alternative: Direct Dispatch

Skip the pull request and have the application repository call the infrastructure
repository's release workflow directly with the artifact version as an input:

```yaml
      - name: Trigger the infrastructure release
        env:
          GH_TOKEN: ${{ steps.token.outputs.token }}
        run: |
          gh workflow run release-app-notifier.yml --repo <org>/infra \
            --field environment=dev \
            --field lambda_s3_key="$LAMBDA_S3_KEY" \
            --field lambda_s3_object_version="$LAMBDA_OBJECT_VERSION" \
            --field lambda_source_code_hash="$LAMBDA_SOURCE_CODE_HASH"
```

The infrastructure workflow then writes those inputs into a runner-local tfvars
file before calling the deploy script — the same second `-var-file`, materialized
from workflow inputs instead of from git.

Choose this when release latency genuinely matters and a pull-request round trip
is the bottleneck. Accept two consequences: the deployed version exists only in a
workflow run's inputs, so "what is deployed" is an API query rather than a file,
and the application repository holds a token that can start an infrastructure
apply — a smaller privilege than applying directly, but not nothing.

Do not run both models for one service. Two writers for the deployed version means
whichever ran last wins the next time the other one runs, with no warning — the
same failure mode as running two task-definition owners against one ECS service.

## Rejected Alternatives

| Approach | Verdict |
|---|---|
| Infrastructure resolves the newest artifact at plan time (`describe-images`, latest S3 version) | Rejected — reintroduces "whatever is newest", so a skipped build silently redeploys or a half-published artifact deploys. The no-default artifact variable exists to prevent exactly this. |
| Application repository assumes `AppDeployRole` and applies the stack itself | Rejected — the split's only security gain is that application CI cannot apply. This gives it back while keeping every cost. |
| Each service repository owns its own app-stack Terraform | Defensible at real scale, but not the default: shared `modules/`, the backend convention, the environment files, and the platform SSM contract all get duplicated per repository and drift. Adopt only with a published, versioned module registry. |
| Git submodule or subtree of `infra` inside the application repository | Rejected — a pinned submodule makes the deployed Terraform version a third thing to reason about, and updating it is a commit in both repositories anyway. |
| Application repository pushes straight to the infrastructure repository's `main` | Rejected — skips the plan the pull request exists to produce, and gives the application repository write access to the default branch of the repository that controls production. |
